# 故障处置（采集全程适用）

按现象分级处置。总原则：**瞬时性问题重试，确定性问题如实上报，账号问题停下来找用户**。

## 1. 412 / 挑战页（瑞数 WAF）

- 现象：请求返回 412，或页面出现空白壳/挑战脚本后迟迟不渲染。
- 处置：
  1. 等待 5-10s 让挑战链走完，刷新一次（最多 1 次）；
  2. 仍失败 → 当前申请号记 `error`，failReason=`WAF拦截`，**不要连续刷新**（高频刷新加重风控）；
  3. 连续 2 个申请号都被拦 → 停止本批，告知用户「平台风控收紧，建议 30 分钟后再跑」，剩余号码全部记 `error`。

## 2. 掉线（URL 回到 SSO 域）

- 见 `login-guide.md` 掉线恢复节。要点：立即停、不自动重登、同会话掉线 ≥3 次建议改期。

## 3. 空结果 / 结果异常

| 现象 | 判定 | 处置 |
|---|---|---|
| 「共查询到 0 条结果」 | `not_found` | 不重试，对账时请用户核对号码 |
| 页面 toast/校验提示「申请号不正确」类 | `not_found` | 同上 |
| 结果总数一直不变（疑似没提交成功） | `error` | 重试 1 次（重新重置表单再查）；仍失败记 `RETRYABLE:查询提交未生效` |
| 首行申请号与输入不一致 | `error` | 记 `RETRYABLE:结果串扰`，重置表单后重试 1 次 |

## 4. 弹窗 / 页面结构异常

- 免责声明、公告弹窗：点「我知道了」/「同意」/「关闭」后继续，属正常流程。
- 详情页「申请信息」区块折叠：点「展开」后再读值。
- 费用树点开无表格 / 应缴费表不存在：按「已授权但费用表未渲染」走 `error` + `RETRYABLE:` 当场重试 2 次（间隔 3-5s）。
- 出现完全未知的页面结构（选择器全部失灵）：**停止本批**，逐条记 `error` + failReason=`页面结构变更`，提示用户本 SKILL 的 playbook 可能需要更新，不要硬猜选择器。

## 5. MCP 推送失败

- `check_token` 返回 invalid：停在最前面，请用户核对/重新下发 token，**不开始采集**。
- `push_fee_batch` 网络失败：整批重推 1 次（幂等，同 dedupKey 覆盖不报错）。
- 返回**权限 / scope 不足**（如「开放接口凭证缺少 scope【patent:fee:ingest】」）：**确定性错误，不重试**。注意 `check_token` 只校验身份、不校验 scope，此时仍可能返回 `valid=true`，**不要**据此认为凭证可写。处置顺序：立即停止推送 → 把已归一的 payload 落盘保存（补权限后可原样幂等重推，**无需重新登录或重新采集**）→ 请用户到 SaaS「个人设置」重新下发 token 时授予 `patent:fee:ingest`（年费采集写入）权限。
- 返回 `rejected` 非空：仅重推被拒条目 1 次；仍被拒则如实列入对账汇总，标注 SaaS 拒绝原因，**不要篡改数据凑接受**。
- **字段级校验被拒**（如「费用状态非法（仅支持 UNPAID/DEFERRED/REDUCED）」）：按报错字段退回对应翻译规则修正。`feeStatus` 只接受三值，表外状态（如 `费足`）**整笔丢弃**，禁止改写状态凑合。
- **payload 顶层字段缺失（调用前的参数校验，非服务端）**：`payload` 的 `batchId` / `collectedAt` / `dataSource` / `failed` / `patents` / `succeeded` / `total` **七项全部必填**。手工拼 payload 时最容易漏 **`succeeded` 和 `total`**（它们只是客户端自报的计数，直觉上像可选项，其实不是）。症状是**调用根本没发出去**，返回 `Parameter validation failed ... must have required property 'succeeded' / 'total'` 并回显完整 schema。处置：补上这两个字段（`succeeded` = 批内 `queryStatus == ok` 的专利数，`total` = 批内专利总数）后重发，**不消耗服务端幂等额度**（请求未到达）。
- **写库约束失败**（如 `null value in column "type" of relation "patent_info" violates not-null constraint`）：属**服务端缺陷，客户端无法绕过**。证据链：`push_fee_batch` 的工具 schema 由服务端 DTO 自动生成，其中没有该字段；实测挂 `type=发明专利` 与 `patentType=INVENTION` 各推一次均被**静默忽略**（不报 schema 错、仍报 null），证明客户端无从补传。报错回带的 `Failing row contains (...)` **会泄露该表的完整列序**——本次即据此确认 `type` 在第 3 列（紧随 `apply_no`）。整批未入库，费用数据随事务回滚。处置：payload 落盘 → 如实报给用户，附报错原文、约束列名与「字段不在契约内」的证据 → 等服务端修复后原样幂等重推。**不要**用默认值、中文类型名或猜测编码去凑这个字段（`patent_type` 同时是 `fee_rule` 查表键，错值会让年费规则整体错配，比留空更危险）；正确修法见 `query-playbook.md` › patentType 推导（服务端从 applyNo 第 5 位算，客户端永不传）。若想改走暂存+人工确认（`submit_patent_data`），属另一条路径，**须用户明确同意后再切**，不要自行绕道。（本次 `patent_info.type` 缺陷已于 2026-09-22 20:08 由服务端修复，同一 payload 原样重推即通过 `received=11 accepted=11 rejected=[]`；本条保留作为此类故障的通用处置。）
- **失败时返回的不是 JSON**：`check_token` / `list_*` 成功时是标准 JSON，但 `push_fee_batch` 一抛异常就返回**裸数据库异常文本**（`ERROR: <PG 异常>` + `详细：<DETAIL>`），**没有 `received`/`accepted`/`rejected` 结构**。所以别指望从失败响应里读 `rejected` 去补推——那只在参数校验级拒绝时才存在；写库级崩溃只能整批修复后原样重推（假设 payload 已落盘）。

## 6. 长任务静默执行（用户零感知）

- 现象：把整批采集塞进**一次命令调用**，用户在整个过程中看不到任何输出 —— 单次工具调用的输出要等结束才回流，且会被 UI 折叠。
- 处置：**一条一次调用**，每条完成立即播报一行进度（格式见 `query-playbook.md` › 逐条进度播报）。**失败条目也必须播报**，禁止静默 `continue`。
- 这是硬性要求而非可选优化：曾 50 条静默跑完，用户明确反馈「没感知」。用户对长任务的期待是**看得见进度**，不是「结束了一次性告知」。

## 7. 输入框填充未生效（fill 静默失败）

- 现象：`bsk fill --value "<申请号>"` 返回成功，但输入框实际仍为空 → 点查询后「共查询到 0 条结果」，与「真的查无此号」长相完全一致（同 §3 第一行）。
- 原因：前端框架（Quasar / v-model）未捕获程序化设值派发的 `input` 事件。
- 处置：**填充后必须回读校验**输入框值是否等于申请号；不一致立即降级为逐字符 `press` 重打，再校验一次；仍不一致才判 `TYPEFAIL`。
- 站点 `fill` 可用时快得多（15 位申请号逐字符敲要 1–2.4s），但**不要为省这一步而省掉回读校验** —— 静默失败会伪装成「查无此号」。
